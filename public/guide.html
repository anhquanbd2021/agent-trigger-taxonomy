Three triggers, three questions

"Keep the agent running" is not one mechanism. The trigger you pick decides when control logic fires — and each wrong pairing fails in a different, predictable way.

The taxonomy

TriggerQuestion it asksFires whenNatural fit
goal (condition)"Are we done yet?"After every unit of work, an evaluator inspects state and decides continue-or-stopConverging tasks with a checkable finish line — migrations, refactors, backlogs
cron (clock)"Is it time to run again?"On a fixed schedule, regardless of stateRecurring work with no end state — polling, monitoring, periodic checks
hook (event)"Did a turn just happen?"After every turn, across sessionsCross-cutting policy — budget guards, audit logging, forbidden-action gates

The three workloads

  • Schema migration (converging) — 40 files, +7 per run. Done is checkable: migrated >= total.
  • Uptime monitor (recurring) — a 10-slot timeline with an outage at slot 4. There is no "done".
  • Budget guard (cross-cutting) — 8 ambient turns across two sessions spend 4–7 units each; the cap is 20 and turn 5 breaches it.

What each mismatch buys you

  • goal × monitor — "are we done yet?" has no answer; the loop burns to the safety cap (8 iterations) and still can't say anything about uptime.
  • cron × migration — the clock can't see the finish line; it keeps paying for runs after the work is complete (4 wasted runs).
  • hook × monitor — checks only happen when a turn happens; the slot-4 outage sits in an idle gap and is missed entirely.
  • goal × guard — the evaluator inspects its own context; the spend lives in other sessions' turns, so there is nothing to check.
  • cron × guard — the breach is detected on the next tick, after the damaging turn already ran; sampling can never block.
  • hook × migration — progress rides whatever sessions happen to turn; work fires on unrelated turns and idles when the world is quiet.

The evaluator inspects — it never executes

In goal mode, two roles are separated: the executor does work and changes state; the evaluator reads state through a read-only view and returns a verdict. In this lab that separation is enforced by code — the evaluator receives a proxy that throws on any write. A condition like "did the migration finish" is a question about the world, not a tool call.

Honest limits

  • This is a deterministic model of trigger semantics — when control logic fires. It is not an LLM, and run() does scripted work, not reasoning.
  • Costs are abstract units (2 per run), not dollars; real waste scales with model and tool pricing.
  • Real systems combine triggers — a goal loop with a stop-hook budget cap is the common pairing; the lab treats them separately on purpose.
  • Hooks here model the after-each-turn kind (stop/notification hooks); pre-tool hooks that gate individual tool calls are a related but distinct layer.
  • Timeline "slots" are a simulated clock; nothing real sleeps or schedules.
